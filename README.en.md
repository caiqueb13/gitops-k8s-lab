# Multi-cluster GitOps lab: k3d/K3s, OCM, Flux CD, Helm, and Kyverno

This lab tests GitOps bootstrap and reconciliation on local Kubernetes clusters. It uses [k3d](https://k3d.io/), which runs K3s in containers and is convenient for creating multiple clusters on one computer. It is lighter than Kind clusters in many scenarios, although each cluster still uses memory and CPU. k3d requires Docker or another compatible runtime. By default, the script pins K3s to `v1.34.12-k3s1`: Docker Desktop in this environment exposes cgroup v1, which the Kubernetes 1.35 kubelet series does not accept by default. Kubernetes 1.34 reaches end of life on 2026-10-27; migrating the local runtime to cgroup v2 is the recommended next step. On cgroup v2 hosts, pass a maintained K3s image with `-K3sImage`.

The names `aks-sim`, `eks-sim`, and `gke-sim` are labels for local clusters only. k3d/K3s does not emulate IAM, networking, managed control planes, or AKS, EKS, and GKE specific integrations.

## Architecture and discovery limits

- Each cluster runs its own Flux and reconciles the same Git configuration.
- Bootstrap creates `GitRepository/lab-config` and `Kustomization/kyverno`. The app manifests contain only the namespace and Helm resources, so reconciliation does not replace the bootstrap URL with a placeholder.
- `HelmRepository` and `HelmRelease` install Kyverno. `version: "*"` demonstrates discovery of new versions; it is not a recommended production policy.
- `sync-k3d-fleet.ps1` queries active k3d clusters and bootstraps their matching contexts. `watch-k3d-fleet.ps1` repeats local discovery every minute.
- On Windows, bootstrap replaces the local `host.docker.internal` endpoint generated by k3d with `127.0.0.1` to reach the port published by Docker Desktop.
- A manually created k3d cluster appears in the next scan. When a fleet-managed cluster is deleted, the next scan removes its OCM entry without trying to contact it. Old kubeconfig entries may remain, but they are not part of the active fleet.

This discovery is local to the computer and k3d runtime. OCM records local clusters after onboarding, and the audit checks their status. For cloud clusters created through a console, CLI, or IaC, kubeconfig is not a universal inventory. A reconciler must periodically query each provider's management APIs (Azure Resource Manager, AWS EKS/Organizations, and Google Cloud Resource Manager/GKE) with read-only credentials, compare inventories, and obtain short-lived Kubernetes credentials for bootstrap. Deletion should remove the inventory entry without contacting a cluster that no longer exists. The cloud reconciler and provider integrations are outside this lab. There is no generic Kubernetes mechanism that discovers arbitrary clusters without an inventory source and credentials.

## Windows prerequisites

- Windows 10/11 and PowerShell 7 recommended (the scripts also use .NET APIs available in Windows PowerShell 5.1).
- Docker Desktop/Engine running, or a runtime compatible with k3d.
- `k3d`, `kubectl`, `flux`, and `clusteradm` on `PATH` for the OCM workflow.
- A Git repository reachable over HTTPS by the clusters. Use a public repository to start. Private repositories require a Flux Secret configured outside Git.

Check the tools before starting:

```powershell
Get-Command k3d, kubectl, flux, clusteradm, git
docker info
```

If Windows blocks scripts because of the Execution Policy, do not change the global policy. Run each script in a process with a temporary bypass, for example:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\new-k3d-cluster.ps1 -Name aks-sim -GitUrl $GitUrl
```

Replace the file and arguments for the command you intend to run. In PowerShell 7, use `pwsh.exe` instead of `powershell.exe`.

## Prepare the local OCM hub

The OCM hub is a separate k3d cluster that stores the inventory. The script creates `ocm-hub` if needed and initializes OCM. It does not install Flux/Kyverno on the hub or create cloud resources:

```powershell
./scripts/new-ocm-hub.ps1
```

The default hub context is `k3d-ocm-hub`. On Ubuntu, install `jq` in addition to k3d, kubectl, Flux, and clusteradm, then use the Bash equivalent:

```bash
bash scripts/linux/new-ocm-hub.sh
```

Onboarding installs components in the target cluster and requires the Kubernetes identity in that context to have enough permissions to create CRDs, deployments, and RBAC. Spokes must be able to reach the local OCM hub. `--force-internal-endpoint-lookup` is intended for this lab's local clusters; remote clusters need a network-reachable hub endpoint.

## Create three local clusters

From the workspace root:

```powershell
$GitUrl = 'https://github.com/caiqueb13/gitops-k8s-lab.git'
./scripts/new-ocm-hub.ps1
./scripts/new-k3d-cluster.ps1 -Name aks-sim -GitUrl $GitUrl
./scripts/new-k3d-cluster.ps1 -Name eks-sim -GitUrl $GitUrl
./scripts/new-k3d-cluster.ps1 -Name gke-sim -GitUrl $GitUrl
```

Run `new-ocm-hub.ps1` first. The cluster script checks binaries, creates the cluster, installs/reconciles Flux, applies bootstrap, waits for Kyverno to become Ready, and registers the spoke in OCM. The k3d context is named `k3d-<name>`.

Equivalent Ubuntu flow:

```bash
GitUrl='https://github.com/caiqueb13/gitops-k8s-lab.git'
bash scripts/linux/new-ocm-hub.sh
bash scripts/linux/new-k3d-cluster.sh aks-sim "$GitUrl"
bash scripts/linux/new-k3d-cluster.sh eks-sim "$GitUrl"
bash scripts/linux/new-k3d-cluster.sh gke-sim "$GitUrl"
```

## Discover manually created k3d clusters

A one-time scan reconciles all active k3d clusters matching the pattern (by default, `k3d-*`):

```powershell
./scripts/sync-k3d-fleet.ps1 -GitUrl $GitUrl -HubContext k3d-ocm-hub
```

For continuous discovery while this PowerShell session remains open:

```powershell
./scripts/watch-k3d-fleet.ps1 -GitUrl $GitUrl -HubContext k3d-ocm-hub -IntervalSeconds 60
```

For example, create a fourth cluster manually in the same Docker Desktop. The next scan will find it in the k3d inventory and install Flux/Kyverno:

```powershell
k3d cluster create dev04 --image rancher/k3s:v1.34.12-k3s1 --wait --timeout 5m
./scripts/sync-k3d-fleet.ps1 -GitUrl $GitUrl -HubContext k3d-ocm-hub
```

With `watch-k3d-fleet.ps1` running, onboarding happens on the next scan. When a cluster is deleted (`k3d cluster delete dev04`), it stops being a target and its OCM entry labeled `k3d-fleet` is removed in the next scan. An old context, if it remains in kubeconfig, is ignored because `k3d cluster list` is the authoritative local source.

The watcher must keep running. It is not a Windows service and does not survive logout or reboot. For continuous operation, a scheduled task can be created after validating the workflow; it must use the same account and runtime that own the k3d clusters. Discovery occurs within one interval after creation. When the watcher stops, new clusters will not be onboarded until the next scan.

On Ubuntu, run `bash scripts/linux/sync-k3d-fleet.sh "$GitUrl"` for a one-time scan or `bash scripts/linux/watch-k3d-fleet.sh "$GitUrl"` for continuous discovery. Set `HUB_CONTEXT` to use a different hub context.

## Onboard an existing cluster

An existing cluster already available in kubeconfig does not need to be recreated. Select its exact context; the script checks access, installs Flux only if absent, configures the Git source and Kyverno, and registers the cluster in the hub:

```powershell
$Context = 'k3d-existing'
$GitUrl = 'https://github.com/caiqueb13/gitops-k8s-lab.git'
./scripts/onboard-existing-context.ps1 -Context $Context -GitUrl $GitUrl -HubContext k3d-ocm-hub
```

If Flux is already installed, the script checks controller health. A partial installation or conflicting `GitRepository/lab-config` / `Kustomization/kyverno` configuration stops onboarding to avoid silently overwriting resources. The context needs permission to install Flux and create the lab resources. For a private repository, `-GitSecretName` references an existing **Kubernetes Secret** in the target cluster's `flux-system` namespace. It contains the read credential that Flux's `source-controller` uses to clone Git (for example, HTTPS credentials or an SSH key). It is not a GitHub Actions Secret, and the script never accepts or reads its values:

```powershell
./scripts/onboard-existing-context.ps1 -Context $Context -GitUrl 'https://github.com/org/private-repo.git' -GitSecretName github-auth -HubContext k3d-ocm-hub
```

The script only checks that the Secret exists and writes its name to `GitRepository/lab-config.spec.secretRef`; the values stay in the cluster. The current bootstrap uses generic Git authentication through `secretRef`. GitHub App credentials also require `spec.provider: github`, which this local flow does not configure yet. In production, create that Secret through a trusted vault/synchronization path and configure the matching provider. Omit `-GitSecretName` for this lab's public repository. On Ubuntu:

```bash
bash scripts/linux/onboard-existing-context.sh --context k3d-existing --git-url 'https://github.com/caiqueb13/gitops-k8s-lab.git' --hub-context k3d-ocm-hub
```

## Audit inventory and health

The auditor reads OCM `ManagedCluster` inventory, checks each registered context, verifies the four Flux deployments, `GitRepository/lab-config`, `Kustomization/kyverno`, `HelmRelease/kyverno`, and Kyverno pods. It stores audit states and the last audit time as annotations on the OCM object. Output is a table by default, with JSON and CSV options:

```powershell
./scripts/audit-ocm-fleet.ps1
./scripts/audit-ocm-fleet.ps1 -Format Json -FailOnUnhealthy
```

On Ubuntu:

```bash
bash scripts/linux/audit-ocm-fleet.sh
FAIL_ON_UNHEALTHY=true bash scripts/linux/audit-ocm-fleet.sh json
```

`Ready` means the configured checks passed at that time; it is not a full cluster security audit. The auditor needs valid kubeconfig contexts for the hub and each registered spoke.

## Access a cluster and verify components

Use the `k3d-<name>` context to access a cluster. Check the active context before running commands to avoid acting on the wrong cluster:

```powershell
kubectl config get-contexts
kubectl config use-context k3d-aks-sim
kubectl config current-context
```

You can also pass `--context` to each command without changing the active context. Verify the installed components:

```powershell
k3d cluster list
flux get all -A --context k3d-aks-sim
kubectl --context k3d-aks-sim get pods -n kyverno
kubectl --context k3d-aks-sim get helmreleases -n flux-system
kubectl --context k3d-aks-sim get pods -n flux-system
```

Wait for Flux resources to show `Ready=True`, Kyverno pods to be `Running`, and the `kyverno` HelmRelease to be `Ready=True`. Repeat with `k3d-eks-sim` and `k3d-gke-sim` to validate the other clusters. To inspect status and failure events:

```powershell
flux get sources all -A --context k3d-aks-sim
flux get kustomizations -A --context k3d-aks-sim
flux get helmreleases -A --context k3d-aks-sim
kubectl --context k3d-aks-sim describe helmrelease kyverno -n flux-system
```

Edit the manifests, commit, and push; clusters check Git about every minute and reconcile the Kustomization about every five minutes. `HelmRelease Ready` confirms release reconciliation, but is not a full audit of cluster health or security.

## Chart updates

`version: "*"` tracks the latest stable version found in the Helm repository. A new version may be incompatible or fail during installation. For production, pin an approved version and use Renovate to propose pull requests, validate first on a canary cluster, then promote to the others with a rollback plan.

## Azure identity, private GitHub repositories, and secrets

For a fleet of dozens or hundreds of existing AKS clusters, keep inventory/onboarding identity, Flux identity, and repository credentials separate. The Azure reconciler's UAMI does not authenticate to GitHub.

**Recommended AKS path:** inventory clusters through Azure Resource Graph/ARM and use Azure Policy `DeployIfNotExists` to install the Flux extension and configuration on existing and new clusters, scoped to a subscription or resource group. Give the policy assignment's managed identity only the ARM permissions needed to remediate extension/configuration resources. This avoids distributing admin kubeconfigs to a central service. Start with a small canary group, inspect status, then roll out gradually. See [Azure Policy at scale for GitOps](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/use-azure-policy-flux-2) and the [DeployIfNotExists effect](https://learn.microsoft.com/en-us/azure/governance/policy/concepts/effect-deploy-if-not-exists).

**Self-managed alternative:** an automation process can use Entra/UAMI credentials to access clusters and install Flux directly. Azure RBAC on the ARM plane and Kubernetes authorization are separate controls. `Azure Kubernetes Service RBAC Cluster Admin` grants administrative access to the cluster; do not assign it broadly for convenience. Restrict scope and duration, protect the runner, and prefer the managed extension when it meets the requirements. See [AKS kubeconfig access and permissions](https://learn.microsoft.com/en-us/azure/aks/control-kubeconfig-access).

For a private GitHub repository, Flux needs Git credentials in each cluster. GitHub Actions Secrets are consumed by Actions workflows; cluster pods cannot fetch those values directly. For self-managed Flux, prefer a read-only GitHub App and store its private key in Azure Key Vault. External Secrets Operator can sync it into a local Kubernetes Secret using Workload Identity. Flux uses the GitHub App data to obtain short-lived installation tokens. Establish the workload identity and secret provider through a trusted bootstrap path first; do not depend on a private repository to deliver the credential needed to clone that same repository. See [Flux GitHub App authentication](https://fluxcd.io/flux/components/source/gitrepositories/).

The App private key is long-lived and must be rotated manually: create a second key, update the vault, wait for synchronization, verify Flux reconciliation across clusters, then revoke the old key. Installation tokens are short-lived and Flux renews them as it authenticates. For the Azure Flux extension, use documented mechanisms (HTTPS/SSH, provider, and local Secret/`localAuthRef`) and confirm support in the selected extension version instead of assuming every self-managed Flux authentication mode is exposed. See [Flux extension Git/Secret parameters](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/gitops-flux2-parameters) and [GitHub App key rotation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps).

Credentials for charts such as Wiz follow the same pattern: keep the service account in a vault, sync it only to the namespace required by the chart, and grant the narrowest available scope, ideally with separate credentials per environment/cluster. Do not put the service account in Git or GitHub Actions Secrets expecting the cluster to read it.

## Stop and remove the local lab

To stop the lab and free CPU and memory, stop the watcher with `Ctrl+C` in the window where it is running. Then check the clusters and stop only the clusters belonging to this lab. Stopping preserves data and workloads for later use:

```powershell
k3d cluster list
k3d cluster stop aks-sim
k3d cluster stop eks-sim
k3d cluster stop gke-sim
```

To resume the lab:

```powershell
k3d cluster start aks-sim
k3d cluster start eks-sim
k3d cluster start gke-sim
```

To permanently delete the clusters, check their names and run the commands individually. This removes the clusters, workloads, and associated local data:

```powershell
k3d cluster list
k3d cluster delete aks-sim
k3d cluster delete eks-sim
k3d cluster delete gke-sim
```

Do not use `k3d cluster delete --all` on a shared machine or one with other clusters. Kubeconfig contexts can be removed separately after checking them, but are not needed for active k3d fleet discovery.

## Cloud and scaling gaps

The local lab validates GitOps, Helm, and bootstrap. It does not yet discover cloud clusters created outside the pipeline. The recommended next increment is a provider inventory with read-only permissions, explicit onboarding state, short-lived credentials, and periodic reconciliation. Add alerts/auditing for provider clusters missing from the Flux inventory and managed clusters whose access was revoked. Provisioning cloud is outside this local lab's scope.

Kyverno is a policy engine and admission controller. It does not replace a visibility agent, log collection, or a CSPM sensor. Add separate charts only when those behaviors become lab requirements.
